## 明亚工作台保单 PDF 批量下载工具

用户给了带 `auth_token` 的明亚工作台链接（`d.mingya.com.cn/workbench-web/#/workBench/myTask/index`），
需求：把任务里的 PDF 保单批量下载。

### 逆向结论（从前端 chunk 确认，可复用）

站点是 Vue3 + Vite SPA，静态资源在 `cdn.mingya.com.cn/workbench/prod/static/js/`。
主 JS 只是入口，业务代码在懒加载 chunk 里（52 个 chunk，共约 4.2 MB）。

**API 基址**：`https://wps.mingya.com.cn/workbench`（运行时注入，变量名 `BASE_WPS_WORK`）。

**鉴权载体 = HttpOnly Cookie `auth_token`，Domain=.mingya.com.cn，不是 header**。
前端 axios 拦截器只注入 `platform: WEB` 头；token 存 sessionStorage 的 `wps_token`，
但真正让接口认的是服务端下发的 Cookie。

**四步链路**：
1. `GET /user/tokenLogin?token=<auth_token>` → 下发 auth_token Cookie
2. `GET /task/list?firstType=1&pageNum=&pageSize=` → 分页取任务（返回 `data.list[].tasks[]`）
3. `GET /task/taskDetail?id=<taskId>` → 返回 `data.fileInfo[]`（id/name/type/creatorName/createTime/url）
4. `GET /file/view?fileId=&taskId=` → 换取该附件真实下载 URL

**关键坑**：PDF「预览」走的是
`https://flow.mingya.com.cn/fileView/onlinePreviewAuth?url=<base64(真实URL)>&watermarkHide=1`
——这是给人眼看的预览页，不是下载口。批量下载必须走 `/file/view` 拿真实 URL。

**auth_token 有时效**：实测用户给的 token 已失效，接口返回 `{"msg":"登录失效","code":401}`。
过期后需重新从打开的工作台页面 URL 里复制。

### 产出

`tools/mingya_batch_download.py` — 完整实现，4 并发下载，按任务建文件夹，
自动跳过已存在文件，`.part` 临时文件保证原子落盘，输出 `_清单.json`。

用法：`python3 tools/mingya_batch_download.py --token MY_xxxx [--list] [--pages N] [--types pdf,xlsx]`

依赖装在 `/Users/apple/.workbuddy/binaries/python/envs/default/`（requests 2.34.2）。

### 追加：token 反复失效后的对策（16:45）

用户把同一个链接贴了两次，token 字符串完全一致（133 字符，含 `MY_*` 星号）。
**注意：第一次测试时我误把 `*` 漏掉了，实际应保留。** 但带 `*` 与不带 `*` 均返回 401。

用伪造 token（`MY_fake_token_for_compare_123456`）对照测试，返回**完全相同**的
`{"msg":"登录失效","code":401}` —— 说明后端对任何无效凭证都统一返回该错误，
无法从错误信息区分「格式错」与「已过期」。结论：该 token 在服务端确为失效状态。

反复贴同一 URL 无效：`auth_token` 是一次性短时效链接（约 2 小时），
必须在门户重新点击入口生成新链接。用户容易从浏览器历史里复制到旧的那条。

**对策：放弃依赖 token，改为复用浏览器实时登录态。**

新增 `tools/mingya_console_download.js` —— 浏览器控制台脚本，
用 `fetch(..., {credentials:'include'})` 直连同一批接口，无需 token：
  - 自动探测登录态，未登录明确报错
  - 遍历 firstType 1/2/3 三类任务，去重
  - `/task/taskDetail` → `fileInfo` → `/file/view` 换真实 URL
  - 按 blob 触发 `<a download>`，700ms 间隔（Chrome 需点一次"允许多文件下载"）
  - localStorage 记录已下项，可重复运行不重复下
  - 失败项打印直链表，可复制用外部下载器

`mingya_batch_download.py` 同时支持 `--cookie "auth_token=xxx"` 直接注入 Cookie 绕过 tokenLogin。

### 关键突破：探针拿到真实响应（21:40）

用户跑 `mingya_probe.js`，彻底定位了 v1 失败原因。**这些是确定结论，后续别再猜：**

**1. 响应结构是 MyBatis-Plus Page，不是 `data.list`**
```
data = { records:[...], total, size, current, orders, optimizeCountSql, searchCount, countId }
```
v1 按 `data.list` 取 → 永远 0 条。**正确字段是 `data.records`。**

**2. 分页参数 `pageNum`/`page`/`currentPage`/`pageIndex` + `pageSize` 全部被服务端忽略**
四组参数返回的 total 都是 523、records 都是 10 条（默认第1页10条）。
响应体里回显 `size` / `current` → 正确参数名应是 MyBatis-Plus 的 **`current` / `size`**（尚未实测验证）。

**3. `/task/listUser` 是免分页捷径**
`GET /task/listUser?firstType=1` 返回 `data.records[].tasks[]`，
一次就把 **523 条**全塞进 tasks 数组，完全不受分页限制。
响应 `list[0]` 字段：userNo/userName/positionNo/positionName/deptNo/deptName/
taskNum/pendNum/finishNum/taskList/tasks。
